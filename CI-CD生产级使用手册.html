CI/CD 生产级使用手册 ​

目标：把“代码能编译”升级为一套可审查、可测试、可发包、可部署、可观测、可回滚的生产交付系统。

覆盖范围：GitHub Actions 与 GitLab CI；Windows、Linux 和 Docker；测试机、预生产机和生产机；NAS、平台制品库与容器镜像仓库；普通云服务与远程手术/医疗设备软件的增强门禁。

CI/CD 不是一份 YAML，也不是“提交后自动复制文件”。它是一条证据链：

第一部分：What——CI/CD 是什么 ​

1. CI/CD 是一套软件交付系统 ​

CI/CD 的本质，是把软件从一次源码变更转换为可验证生产状态的系统。它定义：

  • 哪些输入可以进入交付链；
  • 每一步由谁、在哪台机器上执行；
  • 代码需要通过哪些验证；
  • 交付物如何被唯一标识和保存；
  • 什么条件下允许进入测试和生产；
  • 如何确认发布真的成功；
  • 失败时如何停止、回退和追溯。

它与传统“写完代码 → 手工打包 → 发群里 → 运维拷贝”的根本区别，不是自动化程度，而是状态转换被显式定义，证据由系统自动产生，权限由规则约束。

1.2 CI 和 CD 各自负责什么 ​

**CI（Continuous Integration，持续集成）**回答：“这次代码能否安全地进入共享主干？”

它持续把多人变更集成到主干，通过编译、测试和检查缩短反馈时间。CI 的产物是对源码状态的验证证据，也可以生成发布候选制品。

CD有两种常见含义：

  • Continuous Delivery，持续交付：每个合格版本都达到随时可以发布的状态，但进入生产仍需明确批准。
  • Continuous Deployment，持续部署：合格版本自动进入生产，不再设置人工发布批准。

两者不是成熟与落后的区别，而是风险模型不同。内容网站和低风险内部服务可以持续部署；医疗设备、机器人控制、数据库破坏性迁移通常应持续交付，由人确认维护窗口、临床状态和业务风险。

1.3 CI/CD 不等于 DevOps ​

DevOps 是开发、测试、运维、安全共同对交付结果负责的组织与工程方式；CI/CD 是其中的软件交付机制。部署了 Jenkins、GitHub Actions 或 GitLab Runner，并不代表团队已经形成 DevOps：

  • 开发只负责“流水线绿”，生产故障全部交给运维，不是共同负责；
  • 测试脚本长期失效但为了通过而跳过，不是质量内建；
  • 生产配置靠个人记忆维护，不是基础设施可重复；
  • 发布失败没有观测、停止和复盘，不是闭环。

工具只能执行团队已经明确的规则，无法替代责任边界和工程判断。

2. CI/CD 操作的四种状态 ​

理解 CI/CD，关键不是记平台术语，而是区分四种状态：

状态例子身份主键可以改变吗
源码状态Git commit、依赖锁文件、Dockerfilecommit SHA新提交追加，不改共享历史
构建状态编译器、SDK、构建参数、Runner 镜像pipeline/job ID应被记录并可复现
制品状态ZIP、MSI、tar、固件、OCI 镜像SHA-256 / image digest发布后不可覆盖
运行状态某生产机当前进程、配置、数据库版本environment + instance + deployment ID通过部署受控改变

这四种状态不能混为一谈：

  • commit 通过测试，不代表生产已经运行它；
  • tag 指向 commit，不代表制品已经构建；
  • 文件名写着 v1.8.0，不代表内容没有被替换；
  • 制品部署成功，不代表服务健康或业务成功；
  • Git 回退，不代表数据库、配置和外部协议已经回退。

3. CI/CD 系统的五个平面 ​

3.1 变更控制平面 ​

GitHub/GitLab 仓库、PR/MR、分支保护、CODEOWNERS 和审批规则组成变更控制平面。它回答：谁提出了变更、谁审查、哪些检查必须通过、谁可以批准发布。

3.2 执行平面 ​

Runner、构建机、测试机和硬件台架组成执行平面。它们真正运行不可信代码、编译器、测试和部署命令，因此必须按信任等级隔离。

3.3 制品平面 ​

平台 Artifact、Package Registry、Container Registry、Harbor、NAS 和对象存储组成制品平面。它保存“准备交付的东西”和对应摘要、签名、SBOM。

3.4 部署平面 ​

发布 Runner、部署控制器、SSH/WinRM、OTA 服务、systemd、Windows Service、Docker/Kubernetes 组成部署平面。它把已批准制品转换为目标环境中的运行状态。

3.5 观测与审计平面 ​

监控、日志、告警、部署回执、审计存储和事故系统组成观测平面。它回答发布是否成功、影响是否扩大、何时停止、谁做过什么以及如何复盘。

五个平面可以采用同一家产品，也可以组合使用。例如：

第二部分：Why——为什么要这样设计 ​

4. CI/CD 首先解决反馈成本 ​

软件缺陷的成本随着发现时间上升：开发者本地几分钟发现，只需修改当前上下文；测试阶段发现需要重新打包、沟通和复现；生产发现则可能涉及客户影响、数据修复、合规报告和跨团队事故响应。

CI 的第一价值不是节省测试人员点击按钮的时间，而是把反馈前移并变得稳定：

text
变更越小 → 定位候选原因越少
反馈越快 → 开发者上下文越完整
执行越一致 → “我机器上没问题”越少
检查越自动 → 关键门禁越不依赖记忆

这也是为什么推荐短分支、小批量提交、并行测试和快慢测试分层。把所有测试堆成一个两小时 Job，会让开发者延迟反馈、合并更多变化，最终更难定位失败。

4.1 为什么不能只在发布前集中测试 ​

发布前集中测试会积累一个大批次：多个功能、依赖升级、配置变化和数据库迁移同时进入验证。一旦失败，很难判断是哪一项导致；修复任何问题后又需要重复大范围回归。

正确方式不是取消完整回归，而是建立多层反馈：提交级跑快测试，主干跑集成测试，候选版本跑系统与非功能测试。越靠后证据越接近真实环境，但执行成本也越高。

5. 为什么必须构建一次、晋级同一制品 ​

假设测试阶段运行的是从 commit A 构建的包，生产发布时又在另一台机器重新编译。即使源码 SHA 相同，以下因素仍可能改变结果：

  • 依赖仓库返回了新版本或包被替换；
  • 编译器、SDK、系统库和环境变量不同；
  • 构建脚本依赖时间、网络或未提交文件；
  • 生产机人工修改过源码或配置；
  • Docker 基础镜像的浮动标签已经改变。

于是测试证明的是制品 X，生产运行的却是制品 Y。二者文件名相同也没有意义。

同一个 digest 是否获准进入生产？

5.1 为什么生产机不能 git pull 后现场编译 ​

现场编译把源码、构建权限、生产权限和依赖网络集中在一台机器上：

  • 无法证明生产二进制与测试二进制相同；
  • 生产机需要编译器、包管理器和更广的网络访问；
  • 回滚依赖再次构建，事故时不确定性更高；
  • 人工执行命令难以完整审计；
  • 仓库或依赖服务不可用会直接阻塞恢复。

生产机应该获取已批准、已校验、可离线保存的制品，并只负责安装、启动和验证。

6. 为什么需要测试机、预生产和灰度 ​

6.1 CI Runner 不能替代测试机 ​

托管 Runner 通常是短生命周期的通用虚拟机，适合验证代码逻辑和通用构建；它无法完整代表真实环境中的驱动、Windows Service、systemd、网络 ACL、证书、硬件、杀毒软件、磁盘性能或设备链路。

测试机的价值是验证“制品 + 目标系统 + 配置 + 外部依赖”的组合。它应尽量接近生产，但使用隔离身份和脱敏数据，允许主动制造故障。

6.2 为什么还要预生产 ​

测试环境通常长期被多项开发共享，状态变化频繁；预生产则用于验证发布动作本身：完整部署、数据库迁移、流量切换、监控、回滚和权限路径。预生产不是多买一台服务器，而是为生产变更建立一次低风险彩排。

环境越多不一定越成熟。只有当每个环境有明确目的、入口条件、负责人和退出条件时才有价值；否则只是更多配置漂移。

6.3 为什么不能一次全量发布 ​

测试无法覆盖真实流量、数据分布、时间行为和外部依赖。灰度承认这种认知边界：先让极小范围承担风险，用真实指标判断，再逐级扩大。

灰度降低的是故障半径，不是故障概率。它必须配合：

  • 有代表性的 canary 实例/设备；
  • 明确观察窗口；
  • 业务和技术健康指标；
  • 自动停止条件；
  • 可执行的回滚或流量切回。

没有指标的“先上一台看看”，只是延迟全量，并不是真正灰度。

7. 为什么要隔离权限、保留审批和优先设计回滚 ​

7.1 为什么 Runner 不能直接拥有所有权限 ​

Runner 会执行仓库中的脚本。如果一台 Runner 既运行普通 PR，又保存 NAS 写权限和生产管理员密钥，那么一次恶意提交、依赖投毒或脚本错误就可能越过全部边界。

隔离 build、test-lab、release Runner，是把风险限制在对应阶段：

  • build Runner 可以编译，但不能访问生产；
  • test Runner 可以操作实验室设备，但没有生产证书；
  • release Runner 只接受受保护 ref，能部署但不能修改源码审批结果。

最小权限不是让运维变麻烦，而是让单点失误不能直接变成全系统事故。

7.2 为什么生产仍需要人工审批 ​

自动测试能判断可编码的条件，不能独立判断所有现实约束：当前是否正在手术、客户是否处于关键业务时段、现场是否有回退人员、某项风险是否已被业务接受。

高风险系统中的人不是手工执行每条命令，而是承担不可自动化的风险决策。好的审批页面应展示制品、测试、差异、停止条件和回滚目标；如果审批人只能看到一个“Deploy”按钮，审批只是仪式。

7.3 为什么回滚必须在发布前设计 ​

发布改变的不只代码，还可能改变数据库、配置、缓存、消息格式、设备固件和外部客户端。事故发生后才讨论回滚，会发现旧版本无法读取新数据、升级包改变了 bootloader，或原制品已经找不到。

回滚前置会反向改善设计：

  • API 和数据库采用前后兼容演进；
  • 每次发布保留旧制品和配置；
  • 部署脚本记录 previous version；
  • 健康检查和停止条件可自动执行；
  • 团队通过演练知道恢复权限和时间是否真实。

对于不可逆数据变化，正确策略可能是前向修复，而不是强行回退。因此“回滚方案”更准确地说是“服务恢复方案”。

8. 用一个变更贯穿 What、Why 与 How ​

假设远程服务新增“控制指令去重”，同时修改 Linux 云服务、Windows 控制台和 Docker 部署配置：

  1. 开发者提交代码、单测和协议兼容说明，PR/MR 触发 Windows/Linux 编译、单测、静态分析和容器测试。
  2. 合并后，从明确 commit SHA 构建 Windows ZIP、Linux tar 包和 Docker 镜像；生成 SHA-256、SBOM 和 manifest。
  3. 三种制品进入短期 Artifact/Registry；Linux 测试机和 Windows 测试机自动安装同一批制品，网络模拟器注入延迟、丢包和重复包。
  4. 测试结果与 artifact digest 绑定。测试成功后，发布 Job 把安装包归档到 NAS，只增不改；Docker 镜像按 digest 保存在 Registry。
  5. 预生产使用相同 digest 演练升级和回退，确认旧控制台仍能与新服务通信。
  6. 审批人看到版本、协议风险、测试报告、观察指标和恢复目标，在非手术窗口批准生产。
  7. 先升级一组 canary 云节点，不立即升级所有现场设备；观察重复指令率、超时、错误率和审计日志。
  8. 指标正常后逐步放量。任何停止条件触发，流量切回旧 digest；部署回执记录哪些节点已经升级。

这里每个组件都有明确原因：

做法它解决的问题
PR/MR 自动测试尽早发现逻辑与跨平台问题
测试机和网络注入托管 Runner 无法代表真实系统与链路
构建一次确保测试对象和生产对象相同
NAS/Registry保存并分发不可变制品，支持离线和恢复
摘要、SBOM、manifest回答内容、来源和依赖组成
预生产验证发布与回滚动作，而不只验证代码
审批承担维护窗口与临床状态等现实决策
canary 和停止条件限制未知问题的生产影响范围
部署回执知道实际运行状态并支持精确恢复

下面进入 How：如何把这些原则落实到环境、测试、制品、GitHub/GitLab、Windows/Linux/Docker 和 NAS。

第三部分：How——如何搭建 ​

9. 先建立八条生产不变量 ​

  1. main 始终可构建；失败检查不能靠口头承诺绕过。
  2. 构建一次，多环境晋级：测试和生产使用同一制品摘要，禁止生产机重新编译。
  3. 任一生产实例都能回答：运行版本、commit SHA、制品摘要、构建任务、审批人和部署时间。
  4. 测试机尽量复刻生产机的 OS、运行时、依赖和网络策略，但不复制真实患者数据或生产密钥。
  5. CI Runner 不默认等于生产管理员；生产业务机不直接运行不可信 PR/MR 代码。
  6. 发布失败必须停止，不能带病放量；回滚目标和数据兼容方案在合并前确定。
  7. 密钥不写入仓库、日志、脚本参数或制品；优先使用短期身份，不能使用时才使用受保护 Secret。
  8. 对医疗设备、机器人控制与远程手术链路，自动化可以准备发布，但不能无审批地在手术中更新设备。

10. 实施前再统一术语 ​

10.1 CI：持续集成 ​

CI 在每次提交或 PR/MR 上尽早发现问题，典型任务包括：

  • 格式检查、静态分析、编译和单元测试；
  • 依赖漏洞、密钥、许可证与恶意包扫描；
  • Windows/Linux 跨平台测试；
  • Docker 镜像构建、容器启动和接口测试；
  • 覆盖率、性能基线、测试报告和失败日志留存。

CI 的完成标准不是“Job 是绿色”，而是必需检查覆盖了真正的失败模式，并且报告可定位到明确源码与运行环境。

10.2 CD：持续交付与持续部署 ​

  • 持续交付（Continuous Delivery）：制品随时可发布，但生产部署需要人工或变更流程批准。
  • 持续部署（Continuous Deployment）：通过全部门禁后自动进入生产。

普通低风险 Web 服务可以逐步走向持续部署；远程手术控制、固件、医疗设备现场软件默认采用持续交付，并保留双人审批、维护窗口和现场回退能力。

10.3 Runner：真正执行流水线命令的机器 ​

GitHub 称为 GitHub-hosted/self-hosted runner，GitLab 称为 GitLab Runner。Runner 会检出代码、执行脚本并接触测试网络或凭据，所以它是安全边界，不只是“编译机器”。

Runner 类型适合不适合
平台托管 Linux Runnerlint、单测、普通构建、无内网依赖扫描访问内网 NAS、硬件台架、生产服务器
平台托管 Windows RunnerWindows 编译与通用测试访问公司内网和设备
内网自托管构建 Runner专有 SDK、大型缓存、内网依赖与生产共用管理员身份
集成测试 Runner测试机、数据库、HIL/SIL 台架执行来自外部 fork 的不可信代码
发布 RunnerNAS、Registry、测试/生产部署网络日常 PR 编译和开发者交互登录

推荐隔离：build、test-lab、release 使用不同 Runner 标签和不同服务账号。生产机通常只接受发布 Runner 或部署控制器的单向操作，不在生产业务机上直接安装通用 CI Runner。

10.4 制品：流水线真正交付的对象 ​

制品可以是：

  • Windows：.zip、.msi、.exe、符号文件和配置模板；
  • Linux：.tar.zst、.deb、.rpm、二进制和 systemd unit；
  • Docker：由不可变 digest 标识的 OCI 镜像；
  • 嵌入式：固件、bootloader、升级清单和硬件兼容矩阵；
  • 通用证据：测试报告、覆盖率、SBOM、签名、校验和、构建与部署回执。

源码仓库、制品库和生产机承担不同职责。不要把大体积安装包反复提交到 Git，也不要把平台临时 Artifact 当作唯一长期归档。

12. 从提交到生产的标准流水线 ​

12.1 PR/MR 流水线：快反馈，不接触生产密钥 ​

推荐顺序：

  1. 仓库卫生：格式、生成文件漂移、密钥扫描；
  2. 静态质量：lint、类型检查、静态分析；
  3. 编译与单元测试：Windows/Linux 并行；
  4. 组件测试：数据库、消息队列、协议模拟器；
  5. 安全门：依赖、许可证、SAST、容器扫描；
  6. 构建候选制品并上传短期 Artifact；
  7. 对高风险变更启动测试机/HIL 验证；
  8. 汇总必需检查，失败则禁止合并。

PR/MR 流水线不应把不可信分支部署到长期共享环境；若必须创建预览环境，使用隔离 namespace、短期身份和自动销毁。

12.2 主干流水线：生成发布候选 ​

合并到 main 后：

  • 从明确 SHA 构建一次；
  • 生成版本号、SHA-256、SBOM、签名/证明；
  • 发布到平台制品库或容器 Registry；
  • 自动部署测试机并执行冒烟、集成和回归测试；
  • 测试通过后标记为 Release Candidate，不自动重新构建。

  • 先 canary，再放量；
  • 事后回灌 main，补齐完整回归和事故记录。

13. 生产级自动测试矩阵 ​

13.1 质量门分层 ​

层级典型内容触发频率失败处理
L0 静态检查格式、lint、密钥、许可证每次提交阻止 PR/MR
L1 单元测试算法、业务规则、错误分支每次提交阻止 PR/MR
L2 组件测试DB、队列、文件、协议适配器每次 PR/MR阻止合并
L3 集成/E2E多服务、真实 OS、安装/升级主干/发布候选阻止晋级
L4 非功能性能、长稳、并发、安全、兼容性每日/发布候选超阈值阻止发布
L5 故障与恢复断网、磁盘满、进程崩溃、回滚每周/发布候选无恢复证据不发布
L6 现场/硬件HIL、设备兼容、急停、链路切换关键版本人工签署验证记录

不要盲目规定一个覆盖率数字。核心安全逻辑应达到分支和错误路径覆盖；普通胶水代码可采用较低阈值。更重要的是新代码覆盖率、变异测试、历史缺陷回归用例和未覆盖风险清单。

13.2 Windows 测试重点 ​

  • 目标 Windows 版本、补丁级别、x64/ARM64 与 Visual C++ Runtime；
  • MSI/EXE 静默安装、升级、卸载、重启后恢复；
  • Windows Service 权限、恢复策略、事件日志和防火墙规则；
  • 非管理员用户运行、长路径、中文路径、文件锁和杀毒软件共存；
  • Authenticode 签名和安装包哈希验证。

13.3 Linux 测试重点 ​

  • 目标发行版、glibc、CPU 架构与内核能力；
  • systemd 启停、超时、重启策略、日志轮转和资源限制；
  • 非 root 运行、文件权限、SELinux/AppArmor 与防火墙；
  • .deb/.rpm 升级、卸载、配置保留；
  • 磁盘满、只读文件系统、时钟漂移和网络中断。

13.4 Docker 测试重点 ​

  • 固定基础镜像 digest，不只写浮动标签；
  • 非 root 用户、只读根文件系统、capability 最小化；
  • HEALTHCHECK、启动/优雅退出、资源上限；
  • 容器漏洞、SBOM、镜像来源证明；
  • 数据卷迁移、跨版本 API/DB 兼容和旧镜像回滚。

13.5 远程手术与控制系统增强项 ​

图 6｜自动化可以准备候选制品；改变临床设备状态还需要 HIL、兼容性、双人审批、非手术窗口和离线恢复。

  • SIL/HIL 双层验证，控制算法、设备驱动和真实硬件分开归因；
  • 网络延迟、抖动、丢包、乱序、断链和主备切换故障注入；
  • 连续运行、内存增长、线程优先级、deadline miss 和控制周期尾延迟；
  • 升级失败自动回到已知良好版本；验证 USB 离线升级；
  • 手术中禁止自动更新、自动重启、全盘扫描和大规模数据同步；
  • 更新包签名验证、硬件型号/序列号/bootloader 兼容门；
  • 急停与硬件安全回路不能依赖 CI/CD、容器或云端服务正常运行。

14.3 三类完整性证据 ​

  • SHA-256：发现文件传输损坏或被替换；它本身不能证明发布者身份。
  • 数字签名：证明持有发布密钥的一方批准了内容；私钥应进入 HSM、签名服务或受控密钥库。
  • 构建来源证明/attestation：把制品与源码、构建流程、Runner 和依赖关系绑定。

SBOM 建议使用 CycloneDX 或 SPDX。它不是漏洞报告，而是回答“这个版本包含哪些组件”，便于漏洞响应、许可证审计和现场版本追踪。

15.2 SMB、NFS、SFTP 是什么 ​

  • SMB：Windows 最常见的文件共享协议，路径形如 \\nas01\releases；支持 AD/ACL，Windows 团队易用。
  • NFS：Linux/Unix 常见共享文件系统，挂载后像本地目录；权限常与 UID/GID、网络和导出规则关联。
  • SFTP：通过 SSH 传文件，不是共享文件系统；跨网络边界更容易控制，但不适合作为大量并发随机访问的共享盘。
  • 对象存储：应用通过 API 读写对象，不依赖盘符和挂载；更适合版本化和自动化，但需要 S3 客户端与权限模型。

15.3 本手册采用的默认场景 ​

最常见且容易落地的中型团队场景：

  • GitHub 或 GitLab 保存源码和短期流水线 Artifact；
  • Docker 镜像进入平台 Container Registry 或 Harbor；
  • 公司 NAS 提供 SMB 给 Windows 发布 Runner、NFS 给 Linux 发布 Runner；
  • 两者落到 NAS 的同一个逻辑 releases/<product>/<version> 归档区；
  • 只有发布服务账号可新建版本目录，普通开发者只读；
  • NAS 开启快照、回收站/版本、容量告警和异地备份；
  • 生产环境不从“latest”目录取包，只按版本和 SHA-256 获取。

若团队主要是 Docker/Kubernetes，应以 Registry/Harbor 为在线发布源，NAS 只做灾备导出；若跨地域、大规模或需要对象锁，应优先采用 S3 兼容对象存储。

18.2 部署步骤 ​

  1. 下载明确版本到临时目录；
  2. 校验 SHA-256 和数字签名；
  3. 检查磁盘、OS、依赖、配置与维护窗口；
  4. 解压到新的只读版本目录；
  5. 停止指定 Windows Service；

  7. 启动服务并执行本机健康检查；

21. 数据库、配置和密钥 ​

21.1 数据库迁移 ​

采用 expand → migrate → contract：

  1. Expand：先增加兼容字段/表，旧代码仍可工作；
  2. Migrate：迁移数据和流量，持续校验；
  3. Contract：确认旧版本不再运行后删除旧结构。

破坏性迁移必须有备份、恢复时间验证和前向修复方案。不要假设代码回滚等于数据库回滚。

21.2 配置 ​

  • 配置 schema 与默认模板进入 Git；环境值进入配置系统；
  • 启动前执行配置校验，未知字段默认报错；
  • 测试、预生产和生产只改变环境参数，不改变制品；
  • 配置变更也应有审批、版本和回滚记录。

21.3 密钥 ​

  • GitHub/GitLab Secret 只暴露给受保护 Environment 和发布 Job；
  • 优先 OIDC/短期令牌，减少长期云密钥；
  • NAS 使用独立服务账号；测试和生产凭据分离；
  • 生产 Secret 不进入 PR/MR、普通 Runner、Artifact、Docker layer 或日志；
  • 建立轮换周期、吊销剧本和访问审计。

22. 灰度、健康检查、停止条件与回滚 ​

22.1 健康检查分层 ​

  • 进程存活：只说明程序没退出；

24. 平台与机器的生产安全基线 ​

GitHub/GitLab ​

  • 保护 main、发布 tag 和生产 Environment；
  • 必需检查、CODEOWNERS、非作者审批和职责分离；
  • Runner 分组/标签限制到明确仓库和 protected ref；
  • 第三方 Action/模板固定版本，定期审计供应链；
  • 限制 Job token、fork pipeline 和可修改流水线文件的人员。

自托管 Runner ​

  • 专用主机/VM，禁止作为开发者桌面或生产业务机；
  • Runner 服务账号无交互登录和域管理员权限；
  • Job 后清理工作区，定期重建镜像；高风险任务使用一次性 Runner；
  • 出站域名 allowlist、EDR、补丁、磁盘加密和集中日志；
  • 编译缓存与发布凭据分离；不可信代码永远拿不到发布网络。

测试机与生产机 ​

  • 基础设施和配置纳入版本管理；禁止长期手工漂移；
  • 最小端口、最小用户、时间同步、容量告警和日志轮转；
  • 部署目录与数据目录分离；服务进程非管理员/root；
  • 生产机不安装编译器和源码依赖，除非产品本身有明确要求；
  • 备份必须定期做恢复演练，不能只看“备份任务成功”。

L3 制品化版本、摘要、SBOM、平台 Artifact/Registry制品可反查 SHA 和流水线
L4 测试环境专用测试 Runner/机器、自动部署和回滚测试主干制品可自动验证
L5 受控生产NAS 归档、Environment 审批、灰度和回执同一制品安全晋级生产
L6 韧性治理自动停止、恢复演练、密钥轮换、Runner 重建在目标时间内恢复且证据完整

推荐先做的最小可用版本 ​

两周内先完成：

  1. 建立 Linux、Windows、Docker 三个 CI Job；
  2. 所有脚本落在仓库 ci/，本地与平台共用；
  3. 主干构建版本化包、SHA-256 和 SBOM；
  4. 用一台 Linux 或 Windows 测试机跑自动部署 + 冒烟；
  5. NAS 建立 incoming/products/audit 和只增不改权限；
  6. 生产先采用人工批准，不急于全自动；
  7. 完成一次“坏版本 → 停止 → 回滚”的桌面演练。

完成后再增加签名、HIL、灰度指标、一次性 Runner、Harbor/对象存储和多地区发布。不要一开始同时引入 Kubernetes、复杂 Git Flow、十几种扫描器和自研发布平台。

26. 发布前检查清单 ​

代码与测试 ​

  • [ ] PR/MR 意图单一，必需检查和独立审批通过。
  • [ ] Windows、Linux、Docker 的适用测试通过。
  • [ ] 安全、性能、升级、卸载和回滚风险有证据。
  • [ ] 数据库/API/配置保持前后兼容，或有明确迁移窗口。

制品 ​

  • [ ] 生产制品来自同一已验证构建，没有现场重编译。
  • [ ] 版本、commit SHA、SHA-256、SBOM、签名/证明齐全。
  • [ ] NAS/Registry 中目标版本不可覆盖，权限符合职责分离。
  • [ ] 上一个已知良好版本仍然可获取、可验证、可部署。

环境与操作 ​

  • [ ] 发布窗口、审批人、执行人、观察人和沟通渠道明确。
  • [ ] 测试/预生产与生产差异已列出并评估。
  • [ ] 监控面板、停止条件、回滚命令和数据恢复方案就绪。
  • [ ] 医疗/机器人设备确认当前不是手术状态，现场具备安全接管和离线恢复能力。

发布后 ​

  • [ ] canary 冒烟和观察窗口通过，再逐级放量。
  • [ ] 每台实例/设备的版本、摘要和健康状态可查询。
  • [ ] 部署回执写入平台与审计存储。
  • [ ] 异常、绕过和人工操作进入复盘，而不是留在聊天记录。
